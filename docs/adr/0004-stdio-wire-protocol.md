# ADR-0004 命令式插件 stdio 线协议

- 状态：`accepted`
- 日期：2026-11-16（定稿）
- 决策者：用户（P0 六项批准，按推荐方案定稿）
- 关联：OQ-004（decided）、[DOC-03](../03-plugin-model.md) §5.1、[plugin-spec/02](../../plugin-spec/02-stdio-protocol.md)、[plugin-spec/05](../../plugin-spec/05-errors-and-exit-codes.md)

## 背景

命令式插件通过 stdin/stdout 与宿主通信。必须定义：编码、帧边界、请求/响应结构、日志通道、退出码语义，以及大结果的处理方式。
「一次调用 = 一个进程」，协议不需要多路复用，这大幅简化了设计。

## 决策

**NDJSON（一行一条 JSON，UTF-8）+ stdin 关闭即输入结束 + stdout 只放结果 + stderr 只放日志 + 退出码与响应错误类别一致。**

### 1. 编码与帧

| 项 | 结论 |
| --- | --- |
| 字符编码 | UTF-8（无 BOM） |
| 帧格式 | NDJSON：一行一条完整 JSON，以 `\n` 结束；**不得**跨行 |
| 换行 | 行内禁止裸换行；JSON 字符串内的换行转义为 `\n` |
| 二进制数据 | base64 字符串内联（v1 不提供二进制帧） |
| 未知字段 | 忽略，不报错（[DOC-05](../05-extension-points-and-compatibility.md) §5） |

### 2. 调用时序

1. 宿主启动插件进程（不分配交互式终端）。
2. 宿主向 stdin 写入**一行**请求 JSON，随后**关闭 stdin**——关闭即「输入结束」信号。
3. 插件读取 stdin 至 EOF，解析请求、执行。
4. 插件向 stdout 写入**一行**响应 JSON。
5. 插件向 stderr 写日志（逐行，非结构化结果的唯一通道）。
6. 插件退出，退出码表达结果类别。
7. 宿主以「响应存在 + JSON 可解析 + 退出码为 0 + 响应状态为成功」四者同时成立判定成功；否则失败。

### 3. 请求结构（字段已定稿）

```json
{
  "contract_version": "1.0",
  "capability": "demo-echo.echo",
  "input": { "text": "hello" },
  "context": {
    "invocation_id": "01J8Z0Q3K5V9M2X7",
    "deadline_ms": 5000,
    "subject": "user:alice"
  }
}
```

| 字段 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| `contract_version` | string | 是 | 宿主使用的契约版本，`MAJOR.MINOR` |
| `capability` | string | 是 | 目标能力标识，`<插件标识>.<能力名>` |
| `input` | object | 是 | 能力输入，结构由该能力的输入 schema 定义；无输入时传 `{}` |
| `context` | object | 是 | 调用上下文，见下表 |
| `context.invocation_id` | string | 是 | 调用标识，宿主与插件共用于日志关联 |
| `context.deadline_ms` | integer | 是 | 剩余时间预算（毫秒），插件必须在此内结束 |
| `context.subject` | string | 否 | 调用主体标识；可能敏感，**不得**写入插件日志明文 |

**禁止**在请求中传递明文凭据：凭据由底座在授权后经 `EP-04` 数据目录/配置通道提供，或由插件引用凭据条目。

### 4. 响应结构（字段已定稿）

成功：

```json
{ "status": "ok", "output": { "echo": "hello" }, "plugin_version": "0.1.0" }
```

失败：

```json
{
  "status": "error",
  "error": {
    "code": "input_invalid",
    "message": "字段 text 缺失（必填）",
    "details": { "field": "text" },
    "retryable": false
  }
}
```

| 字段 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| `status` | string | 是 | `ok` 或 `error`，二者互斥 |
| `output` | object | 成功时是 | 能力输出，结构由输出 schema 定义 |
| `plugin_version` | string | 否 | 插件实际版本，供宿主校验 |
| `error` | object | 失败时是 | 结构化错误，见 [plugin-spec/05](../../plugin-spec/05-errors-and-exit-codes.md) |
| `error.code` | string | 是 | 错误类别（枚举见 plugin-spec/05 §2） |
| `error.message` | string | 是 | 面向人的说明，不得含敏感信息 |
| `error.details` | object | 否 | 定位用附加信息（字段名/位置/上游错误摘要） |
| `error.retryable` | boolean | 否 | 是否建议重试；缺省视为 `false` |

要求：成功响应不得携带 `error`；失败响应不得携带 `output`。

### 5. 大结果与体积上限

- **处理方式已定**：插件在序列化前自检体积；一旦预计超限，**必须**返回 `result_too_large` 错误并以非 0 退出码退出，
  **禁止截断后返回成功**，也禁止分段输出（v1 不支持流式）。
- 宿主侧同样自检：读取超过上限即判定失败并终止进程，不得无限缓冲。
- **具体上限数值待定**（属于量化目标，OQ-017），不得在规格中硬编码一个臆造值。
- 超限错误的表达统一使用 `error.code = "result_too_large"`，`details` 可带 `observed_bytes`。

### 6. 日志与 stdout 纯净

- stdout **只**承载那一行响应 JSON；日志、进度、警告、横幅、调试输出一律写 stderr。
- stdout 出现多行、空输出、非 JSON 或夹带日志 → **协议违规**，即使业务成功也判失败。

### 7. 退出码

最终码表见 [plugin-spec/05](../../plugin-spec/05-errors-and-exit-codes.md) §3：`0` 成功；`1` 内部错误；`2` 输入非法；
`3` 能力不支持；`4` 权限/凭据；`5` 超时；`6` 结果过大；`7` 依赖不可用；`8` 协议违规自检。
退出码与响应错误类别**必须一致**；矛盾时按失败处理并记录协议不一致。

### 8. 超时与终止

- 超过 `context.deadline_ms`：宿主终止插件进程，返回超时类错误。
- 终止顺序：先发送温和终止信号，宽限期后强制终止（具体信号与宽限期属实现细节，见 OQ-017）。
- 插件必须可被终止、不得忽略终止信号、不得留下子进程与临时文件。

## 被否方案与原因

| 方案 | 说明 | 否决原因 |
| --- | --- | --- |
| 长度前缀帧 | 先写字节长度再写负载 | 边界更明确、可承载二进制，但实现与人工排查成本高；v1 无二进制需求 |
| 纯文本 CLI 风格 | 位置参数 + 文本输出 | 无法表达结构化错误与结果类型，错误不可归类 |
| 多消息流（请求/进度/结果） | 多次往返 | 与「单次调用、单次结果」语义不匹配，进度上报属 v1 之外能力 |
| 双向长连接 + 多路复用 | 复用进程处理多请求 | 违背 CAP-04「单次调用单次进程」，故障隔离与回收语义变复杂 |
| 用 stdout 同时承载日志与结果 | 便于插件开发 | 结果不可可靠解析，已被证明是最常见的集成故障源 |

## 影响与约束

**正面**：任何语言都易实现；宿主实现简单；人工可直接排查；天然禁止「stdout 混日志」；协议无状态、易重放测试。

**负面 / 代价**：超大结果形成很长的单行（用上限与显式错误兜底）；不支持二进制帧与流式进度；
单次调用固定有进程创建开销。

**实现约束**：

- 插件不得依赖特定工作目录，路径必须基于清单声明或显式参数解析。
- 插件不得要求交互式输入（禁止 TTY 依赖）。
- 协议升级（如引入流式）必须走契约 MAJOR，不得在 NDJSON 上打补丁。

## 验证方式

1. 插件向 stdout 输出一行日志 → 宿主判定协议违规并返回明确错误。
2. 插件不输出响应即退出 0 → 宿主返回「无结果」类失败，不被误判为成功。
3. 退出码非 0 但响应为成功 → 判失败并记录协议不一致。
4. 结果超过上限 → 插件返回 `result_too_large` 且宿主不缓冲超出上限的数据。
5. 超时后进程被终止且无残留子进程。
6. 请求带未知可选字段 → 插件正常执行（向前兼容）。
