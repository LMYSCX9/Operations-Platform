# ADR-0007 持久化存储方案与插件数据边界

- 状态：`accepted`
- 日期：2026-11-16
- 决策者：用户（2026-11-16 确认）
- 关联：OQ-007（已关闭）、OQ-020（已关闭，单节点）、OQ-022（未闭合，默认数据目录）、[ADR-0013](0013-plugin-credential-encryption.md)、[DOC-08](../08-storage-and-data-directory.md)、[DOC-02](../02-foundation-capabilities.md) CAP-10、[DOC-04](../04-plugin-lifecycle.md) §3.6

## 背景

底座需要持久化三类数据（来源：用户实际场景）：

1. 登录用的账号与口令；
2. 插件执行记录与审计事实；
3. 插件访问其他中间件所需的账号口令。

同时必须回答：插件自己的数据放哪里、能否访问底座存储。单二进制定位意味着**不能默认要求外部数据库**，且需支持离线安装与跨平台构建。

## 决策

**采用嵌入式 SQLite（纯 Go 驱动、免 cgo）作为底座唯一的内置存储；插件使用独立数据目录，不直连底座数据库。**

| 决策点 | 结论 |
| --- | --- |
| 存储引擎 | SQLite，嵌入式、单文件 |
| 驱动约束 | 必须为纯 Go 驱动，**禁止引入 cgo** |
| 部署依赖 | 无外部数据库服务，随数据目录存放 |
| 部署形态 | **单节点**（OQ-020 已关闭）；多节点高可用记为远期 idea（DOC-00 IDEA-7），不进 v1 |
| 数据目录 | **由配置文件指定**，必须为绝对路径、必须位于本地文件系统；未指定时的默认回退待确认（OQ-022） |
| 插件数据 | 每插件一个独立目录（EP-04），插件不得直连底座数据库 |
| 写入模型 | 单写者（仅宿主进程写库），详见 DOC-08 §6 |
| 凭据静态加密 | 插件外部凭据用 AES-256-GCM 加密存库，密钥不入库（[ADR-0013](0013-plugin-credential-encryption.md)） |

## 推荐理由（为什么是 SQLite）

1. **符合单二进制部署**：无需安装与运维数据库服务，数据随数据目录走，离线环境可直接落地。
2. **本地单文件**：一个库文件 + WAL 附属文件，便于整体迁移、备份与容量观察。
3. **免 cgo**：纯 Go 驱动使交叉编译与多平台产物可控，不引入 C 工具链与平台动态库依赖。
4. **需要查询能力**：审计与执行记录要按时间、主体、插件、结果等条件过滤，SQL 与索引直接可用；KV 方案需要自行实现索引与查询层。
5. **事务与备份机制成熟**：支持事务、WAL 并发读、在线备份接口，满足一致性与备份要求（DOC-08 §7）。

## 备选方案与放弃原因

| 方案 | 说明 | 放弃原因 |
| --- | --- | --- |
| A. 嵌入式 SQLite（纯 Go 驱动） | 本次选定 | — |
| B. 嵌入式 KV（bbolt 等） | 单文件 KV、纯 Go、事务清晰 | **缺少查询语言**：审计按多条件过滤、分页、聚合需自建索引与查询层，长期维护成本高，统计类需求难以演进 |
| C. 外部数据库（PostgreSQL/MySQL 等） | 独立服务、扩展性强 | **破坏单二进制部署**：需额外安装、端口、账号、备份与升级流程，离线与轻量部署场景不可接受 |
| D. 纯文件（JSON/YAML） | 零依赖 | 无事务与并发控制，崩溃后易出现半写与数据丢失，审计场景不可接受 |
| E. SQLite + cgo 驱动 | 复用成熟 C 实现 | **引入 cgo**：破坏纯 Go 构建与交叉编译，增加平台依赖，与「单二进制、免 cgo」约束冲突 |

## 影响

### 正面

- 零外部服务依赖；备份对象明确（一个库文件 + 备份目录）。
- 审计与执行记录可直接用 SQL 查询，无需自建查询引擎。
- 纯 Go 构建链简单，多平台产物可预期。
- 插件数据隔离边界清晰：数据库不向插件开放，插件只有自己的目录。

### 负面 / 代价

- **单写者模型**：写并发受限，必须用批量写队列与短事务（DOC-08 §6），不能按调用直接抢锁。
- **依赖本地文件系统语义**：SQLite 的文件锁与 WAL 共享内存要求可靠的本地 POSIX 锁，不能放在网络文件系统上（DOC-08 §5）。
- **单文件是单点**：库文件损坏影响面大，必须依赖备份与完整性校验。
- **schema 演进不可降级**：旧版本二进制不能打开新 schema（DOC-08 §8）。
- **不支持多节点**：同一库文件不能被多主机同时使用，v1 明确为单节点部署；多节点高可用属于远期 idea（DOC-00 IDEA-7）。

### 迁移成本

- 若未来切换外部数据库，需要抽象仓储接口；当前**不做多后端抽象**，只保留最小边界，避免过度设计。
- 数据迁移必须通过导出/导入工具完成，不在本次范围。

## 约束（实现必须遵守）

1. 只有宿主进程写库；插件通过能力调用访问数据，禁止直连。
2. 数据目录必须位于本地文件系统，禁止 NFS/SMB/FUSE 同步盘与跨主机挂载。
3. 执行/审计记录走批量写队列，禁止每次调用单独抢写锁。
4. 备份必须使用数据库在线备份接口（或等价的 checkpoint + 一致性快照），禁止运行中直接复制文件。
5. schema 迁移只升不降；遇到更高版本 schema 必须拒绝启动。
6. 库文件、备份文件、含敏感信息的配置权限必须限制为服务账号可读写（DOC-08 §4）。
7. 数据目录必须由配置文件指定，且必须校验为绝对路径与本地文件系统；不得接受相对路径或网络挂载（DOC-08 §4、§5）。
8. 单节点部署：同一数据目录只允许一个底座实例（`.lock`），不支持多实例共享或主备同时挂载。
9. 审计保留期与归档策略、批写阈值、备份频率等数值项待定（OQ-016、OQ-017）。

## 验证方式

1. 断电/异常退出后重启，库通过完整性校验，注册表与审计无半写状态。
2. 插件进程无法读取其他插件目录，也无法打开库文件（权限 + 路径约束）。
3. 通过在线备份接口产出的备份可独立打开并通过完整性校验。
4. 用旧版本二进制打开新 schema 库时拒绝启动并给出明确原因。
5. 高并发调用下写入不出现 `database is locked` 类错误（由批写队列保证）。
