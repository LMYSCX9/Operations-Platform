# ADR-0019 错误类别扩展（契约 1.1）与退出码适用范围

- 状态：`accepted`
- 日期：2026-11-16
- 决策者：用户授权补全（错误类别扩展为明确要求；退出码与 daemon 的关系同步定案）
- 关联：OQ-006（decided）、[ADR-0004](0004-stdio-wire-protocol.md)、[ADR-0005](0005-daemon-rpc-transport.md)、[DOC-03](../03-plugin-model.md) §5.3、[DOC-05](../05-extension-points-and-compatibility.md) §3、[plugin-spec/05](../../plugin-spec/05-errors-and-exit-codes.md)

## 背景

契约 1.0 的错误类别只有 12 个，其中 `input_invalid` 同时承担「结构不合法」「业务校验不通过」两件事，
`capability_unknown` 也被误用来表达「目标对象不存在」。插件作者在写 delete / restore / gc 这类能力时无法准确归类失败，
调用方也无法区分「改输入」「换目标」「等状态变化」三种处置方式。

同时，仓库既有「8 个固定退出码（0~8）」只对命令式插件有意义，而常驻插件没有退出码语义，
两者关系此前只在 plugin-spec 里一句「常驻插件无退出码语义」，未说明进程异常退出如何折算，也未说明旧宿主遇到新错误码怎么办。

## 决策

### 1. 契约版本提升到 1.1（MINOR）

| 项 | 结论 |
| --- | --- |
| 新版本 | `1.1`（底座同时支持 `1.0` 与 `1.1`）；1.2 新增远端形态与 `config[]`，不改本 ADR 的错误类别与退出码规则 |
| 变更性质 | MINOR：只新增错误类别与一个可选上下文字段，不删除、不改名、不改既有取值语义 |
| 生效方式 | 插件声明的范围包含 `1.1` 才允许使用新类别；仍声明 `<1.1` 的插件按 1.0 语义运行，行为不变 |
| 声明示例 | 使用新类别的插件：`contract: ">=1.1 <2.0"`；不使用新类别的插件可保持 `">=1.0 <2.0"` |

### 2. 新增三个错误类别

| `code` | 含义 | 与既有类别的边界 | `retryable` 默认 |
| --- | --- | --- | --- |
| `not_found` | 请求指向的**目标对象不存在**（分区、条目、主机、快照等） | 不是 `capability_unknown`（那表示能力未声明）；也不是 `input_invalid`（结构本身合法） | false |
| `validation_failed` | 结构合法，但**业务校验不通过**（取值冲突、组合非法、超出业务允许范围） | `input_invalid` 只负责结构/类型/必填/枚举取值 | false |
| `precondition_failed` | **前置条件不满足**（状态不允许、顺序未满足、存在进行中的同类操作、锁被占用） | 不是 `dependency_unavailable`（外部依赖不可达）；前置条件通常可通过先完成别的动作解除 | false |

归类规则（写死，避免二次解释）：

1. 字段缺失、类型错、枚举越界 → `input_invalid`。
2. 字段齐全但语义冲突（如 `confirm_partition` 不等于目标分区）→ `validation_failed`。
3. 目标不存在（查无此对象）→ `not_found`。
4. 目标存在但当前状态不允许执行（如快照正在恢复中又发起 restore）→ `precondition_failed`。
5. 外部系统不可达 → `dependency_unavailable`。

### 3. 底座遇到未知错误码的行为

- **不崩溃、不拒绝响应、不自动重试**。
- 对外归一为 `internal_error`；执行记录额外保留插件原始 `code`（`error_category_original` 字段）与插件标识、契约版本声明。
- 记一条「未登记错误类别」告警计数，用于发现插件私造类别；同一插件重复出现按次数聚合，不逐次刷屏。
- 若插件声明范围包含 `1.1` 却返回未登记类别，仍按上述处理（契约要求插件只用登记类别）。

### 4. 退出码只适用于命令式插件

| 形态 | 退出码语义 |
| --- | --- |
| 命令式（stdio） | 有语义：0~8 表达结果类别，必须与响应 `error.code` 语义一致（一致性由宿主校验） |
| 常驻（daemon） | **无语义**：进程退出码只表示进程终止，不表达业务结果；宿主只做诊断记录，不参与协议一致性校验 |

命令式插件退出码保持 **0~8 共 9 个固定值**，不新增 9 及以上（既有规则「9+ 按 `internal_error` 处理」保持不变）。
新增错误类别在命令形态下按下列**桶映射**选择退出码（退出码是粗分类，精确类别以响应 `code` 为准）：

| `code` | 命令式退出码 |
| --- | --- |
| `not_found` | 2 |
| `validation_failed` | 2 |
| `precondition_failed` | 7 |
| 其余 1.0 类别 | 维持原有映射 |

退出码 7 的桶语义在此明确为「依赖不可用**或**前置条件不满足」——这是对既有桶的**澄清**，不改变 1.0 插件的任何行为：
1.0 插件只会用到「依赖不可用」这一面，宿主判定逻辑不变。

### 5. 常驻插件进程异常退出的折算

| 场景 | 对调用方的错误类别 | 说明 |
| --- | --- | --- |
| 启动阶段退出（未就绪） | `not_ready` | 记录退出码/信号与 stderr 尾部 |
| 有在途调用时进程崩溃或被杀 | `internal_error` | `retryable` 由宿主按能力 `idempotent` 判定；记录退出码/信号 |
| 底座主动 `Shutdown` 后正常退出 | 不产生新错误 | 未完成调用已按 drain 结果给出 `cancelled` |
| 无在途调用时崩溃 | 不产生调用错误 | 状态转 `unhealthy`，写审计并触发重启策略 |

折算出的错误**不得**冒用插件的业务类别（如 `not_found`），必须体现为环境/进程类失败，避免调用方误判为业务结论。

## 被否方案与原因

| 方案 | 说明 | 否决原因 |
| --- | --- | --- |
| 继续用 `input_invalid` 承载业务校验 | 不改契约 | 调用方无法区分「改输入」与「换目标/等状态」，只能靠解析 message，违背结构化错误目标 |
| 用 `capability_unknown` 表达目标不存在 | 复用现有类别 | 语义错位：能力存在但目标不存在，会误导排障方向 |
| 新增退出码 9/10/11 | 与错误类别一一对应 | 破坏「9+ 按 internal_error」的既有规则，且所有既有宿主与工具需同步升级；命令形态是粗分类场景，桶映射足够 |
| 只给 daemon 增加新类别 | 改动面最小 | 两种形态共用同一错误模型（INV-6），形态间类别不一致会让调用方写两套判断 |
| 未知 code 直接判协议违规并拒绝 | 严格 | 新宿主遇到旧插件不可能触发；但未来新增类别时会让「宿主先行升级」变成破坏性发布 |
| 未知 code 透传给调用方 | 信息最全 | 调用方无法处理未登记类别；且会让插件私造类别悄悄流入上层 |

## 影响与约束

**正面**：失败原因可被程序化处置；命令形态与 daemon 形态的错误语义彻底对齐；旧插件零改动继续工作。

**负面 / 代价**：底座与 SDK 需维护「已登记类别 + 桶映射」表；调用方需按新类别调整处置分支；
插件若想使用新类别必须把声明下限提到 `1.1`，否则即便返回也会被归一。

**实现约束**：

- 错误类别常量只在 `sdk/` 维护一份（[ADR-0020](0020-contract-source-and-protoc-toolchain.md)），宿主、插件、文档不得各自复制一份枚举。
- 宿主必须校验命令式插件的「退出码 ↔ `code`」同桶；不同桶按 `protocol_invalid` 处理并记录。
- 审计与执行记录必须保存归一前的原始 `code`，便于定位插件契约漂移。

## 验证方式

1. 声明 `>=1.1` 的插件返回 `not_found` → 原样透出，执行记录 `error_category=not_found`。
2. 声明 `>=1.0 <1.1` 的插件返回 `not_found` → 对外 `internal_error`，`error_category_original=not_found`，产生告警计数。
3. 插件返回未登记 code（如 `weird_error`）→ 不崩溃、不重试、归一 `internal_error`。
4. 命令式插件返回 `precondition_failed` 但退出码为 2 → 判 `protocol_invalid`（桶不一致）。
5. daemon 进程被信号杀死且存在在途调用 → 调用方收到 `internal_error`，审计含信号与退出码。
6. daemon 正常 `Shutdown` 退出 → 不产生业务错误，无「异常退出」告警。
7. 旧宿主（仅支持 1.0）遇到 1.1 插件：兼容判定拒绝启用（MAJOR 相同但 MINOR 超出范围），不会出现半支持状态。
