# ADR-0014 SSH 传输与主机凭据管理

- 状态：`proposed`
- 日期：2026-11-16
- 决策者：待定（用户）
- 关联：OQ-010（收窄）、OQ-024~OQ-029、[DOC-09](../09-host-management-and-plugin-distribution.md)、CAP-13、[ADR-0013](0013-plugin-credential-encryption.md)、[ADR-0008](0008-distribution-signing.md)、[ADR-0006](0006-plugin-authz.md)

## 背景

用户需求：Web UI 侧边栏需要「配置主机」入口，可配置 SSH 密钥或账号密码，用于把插件下发安装到目标主机。

这推翻了此前「v1 仅本机」的隐含前提，但推翻的**只是安装位置**这一层，不自动等于「常驻插件的跨主机调用传输已解决」——两者必须分开决策：

| 层次 | 问题 | 本 ADR 是否覆盖 |
| --- | --- | --- |
| 安装位置 | 插件包如何到达目标主机并落地 | 覆盖（SSH 下发） |
| 远端执行载体 | 目标机上的插件由谁启动、如何被调用 | **不覆盖**：已由 [ADR-0018](0018-daemon-process-custody-and-injection.md)（systemd 托管）与 [ADR-0022](0022-remote-plugin-pki-and-mtls-certificates.md)（TCP+mTLS）决定；本 ADR 的 SSH 只用于安装、启停与探测 |

同时必须承认一个安全事实：**底座一旦持有可登录生产机的 SSH 凭据，它本身就是一台高权限跳板机**。这不是「实现细节」，而是必须在规格层显式定性的风险。

## 决策（待确认）

1. 主机连接与凭据管理采用哪种传输与管理方式。
2. 两种认证方式（SSH 密钥、账号密码）的支持策略与凭据保存规则。
3. 主机身份的校验方式（指纹首次信任 / 预置指纹 / 不校验）。
4. 下发安装的执行方式与失败处置边界。
5. **谁能对哪些主机下发**的授权模型。

## 推荐方案与理由

**内置 SSH 客户端作为唯一的远程下发通道；凭据加密落库并复用 ADR-0013 基线；按「主机分组 + 角色范围 + 二次确认 + 全程审计」做授权。**

| 决策点 | 推荐 | 理由 |
| --- | --- | --- |
| 传输 | SSH（Go 内置实现，纯 Go，不引入外部客户端进程） | 与单二进制一致；无外部依赖；运维生态通用；具体库与版本待定 |
| 认证 | SSH 密钥（首选）与账号密码（兼容存量）并存 | 用户明确要求两种；密钥可避免密码扩散，密码用于过渡期与无密钥条件 |
| 凭据存储 | 加密落库（AES-256-GCM，主密钥不入库），保存后不可回显、不可导出 | 直接复用 ADR-0013，避免出现第二套密钥管理 |
| 主机身份 | 首次连接记录指纹（TOFU），后续变更必须告警并要求确认 | 不做「静默信任」，也不强制用户预先录入指纹；策略待拍板（OQ-025） |
| 下发 | 底座推送插件包 → 目标机校验 → 落地安装 → 回报状态 | 下发与执行解耦，失败可定位到具体阶段 |
| 完整性 | 下发前校验插件包摘要；签名是否强制待定（OQ-026） | 与 ADR-0008 的分发校验衔接 |
| 并发 | 按主机串行、跨主机可并行；全局并发上限可配置（默认值待定，OQ-029） | 避免同一主机上多任务互相覆盖 |
| 失败处置 | 保留上一版本、失败即停止并回报；自动回滚是否默认开启待定 | 不允许「半装」状态对外可见 |

理由：SSH 是唯一能同时满足「无外部依赖 + 通用 + 可审计」的通道；凭据复用既有加密基线可避免安全模型分叉；把「安装」与「执行」拆开，可以在运行模型未定时先把用户要的能力做出来，而不假装已经解决了跨主机调用。

## 授权边界（必须由用户拍板）

**风险定性**：底座持有生产机 SSH 凭据后，能做的事远大于「装插件」——可执行任意命令、读取目标机数据。因此下发权限等价于**准 root 权限**，不能按普通业务功能对待。

候选模型（推荐组合使用，最终以用户裁决为准）：

| 候选 | 说明 | 作用 |
| --- | --- | --- |
| A. 主机分组授权 | 主机按分组/标签归属，角色只被授权到分组，不授权到单机 | 缩小爆炸半径 |
| B. 操作二次确认 | 下发前要求显式确认目标主机与插件版本，高危操作可要求再次输入 | 防误操作 |
| C. 全程审计 | 记录谁、对哪些主机、下发了什么版本、结果如何；审计不可被插件修改 | 事后追责 |
| D. 凭据最小化 | 优先使用专用低权限账号或受限密钥；不默认使用 root | 降低凭据价值 |
| E. 下发与启停分离 | 允许「只下发不启用」，启用是另一个受控动作 | 避免下发即生效 |

**必须明确的结论**：这套模型是否落地、粒度多细、是否需要审批流，属于待用户确认项（OQ-028），本 ADR 不替用户决定。若用户不接受「按分组授权 + 二次确认」，则应至少保留「全程审计 + 凭据最小化」，否则不建议开放多主机下发。

## 备选方案与放弃原因

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. SSH（本次推荐） | 标准协议，密钥/密码均可 | 采用 |
| B. 目标机预装 Agent，由 Agent 拉取插件包 | 底座不直接登录主机 | **不采用为 v1 唯一方案**：需要先在每台机器部署 Agent，与「界面配置即可下发」的诉求冲突；可作为 OQ-027 的演进方向 |
| C. 仅 WinRM / PowerShell Remoting | 面向 Windows 主机 | 取决于 OQ-024 的操作系统范围；Linux 为主时作为补充而非基线 |
| D. 仅 Ansible 等外部工具 | 复用既有运维工具链 | 引入外部运行时依赖，破坏单二进制；且授权与审计边界不落在底座内 |
| E. 仅本机安装，不做远程下发 | 维持旧结论 | 与本次用户需求直接冲突，放弃 |

## 影响

### 正面

- 满足「在界面配置主机并下发插件」的核心诉求，不需要额外运维工具。
- 凭据加密与不可回显复用 ADR-0013，安全模型不分裂。
- 主机清单、下发状态、失败原因成为可审计的一等数据。

### 负面 / 代价

- **底座成为高权限跳板**：主机被攻破的影响面显著扩大；ADR-0013 的边界（不防主机被完全控制）在此场景下更敏感。
- SSH 协议细节（算法协商、密钥类型、老版本服务端兼容）会带来持续维护成本。
- 下发失败、网络中断、目标机磁盘不足等外部故障必须显式建模，不能当异常吞掉。
- 目标机上的插件包与数据目录需要新的生命周期规则（升级、卸载、残留清理）。
- 远端执行载体已定（ADR-0018 / ADR-0022）后，「下发成功」仍不等于「已启动」或「可被调用」，必须在 UI 上如实区分三态。

### 迁移成本

- 若后续改为 Agent 拉取模式（方案 B），主机清单与授权模型可复用，传输层需替换。
- 若后续支持 Windows，需要新增传输实现与路径/权限语义适配（OQ-024）。

## 约束

1. SSH 私钥与账号密码**必须加密落库**，复用 ADR-0013 的算法与密钥来源；保存后不可回显、不可导出明文。
2. 连接与下发全过程不得在日志、审计详情、错误信息中出现凭据明文。
3. 每次连接必须校验主机身份；校验策略未定前按「首次信任 + 变更告警」实现（OQ-025）。
4. 下发必须可重试且幂等：同一主机同一版本重复下发不得产生重复安装或损坏状态。
5. 下发失败不得留下「已安装」的假象；状态必须与目标机实际落地情况一致。
6. 下发是高危操作，必须审计；是否强制二次确认与分组授权待用户拍板（OQ-028）。
7. 目标主机操作系统范围未定前，**不得**假定只有 Linux，也不得提前实现 Windows 专用逻辑（OQ-024）。
8. 具体 SSH 库、端口、远端路径、执行命令均**待定**，不得在规格中编造。

## 验证方式

1. 使用密钥与密码两种方式各成功连接一次目标主机，并在凭据保存后确认界面与接口均无法回显明文。
2. 目标机指纹变化时，连接被阻断或明确告警，且事件可审计。
3. 同一主机同一版本重复下发两次，结果幂等，注册表与目标机状态一致。
4. 网络中断/目标机不可达时，下发任务进入失败态并给出可诊断原因，不产生半装状态。
5. 未获授权的角色无法对目标主机发起下发（授权模型落地后验证）。
6. 审计记录能还原「谁在何时对哪台主机下发了哪个版本、结果如何」。
