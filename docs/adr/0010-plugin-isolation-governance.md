# ADR-0010 插件进程隔离、资源限制与故障治理

- 状态：`proposed`
- 日期：2026-11-16
- 决策者：待定（用户）
- 关联：OQ-009、OQ-012、[DOC-04](../04-plugin-lifecycle.md) §4、NFR-REL-01

## 背景

插件是不可信代码（DOC-06 §6.1）。需要确定隔离强度：仅 OS 进程隔离，还是引入容器/沙箱；以及插件崩溃、超时、健康检查失败后底座如何处置。

## 决策（待确认）

1. 隔离边界。
2. 资源限制是否启用。
3. 故障处置策略（重启、熔断、自动禁用）。

## 推荐方案与理由

**OS 进程隔离为基线；资源限制可选启用；异常退出按退避重启；健康检查失败短路调用**

- 隔离：插件运行在独立进程（命令式插件天然每次一个新进程；常驻插件独立常驻进程），不共享地址空间。
- 资源限制：可选启用 CPU/内存/文件句柄限制（平台能力差异大，具体机制待定），默认不强制，避免与部署环境冲突。
- 重启：常驻插件异常退出 → 按指数退避重启，超过阈值进入 `unhealthy` 并停止自动重启，等待人工介入或配置恢复。
- 熔断：健康检查连续失败 N 次 → `unhealthy`，调用直接返回不可用错误（OQ-012 定阈值）。
- 超时：所有调用由宿主强制超时；超时后终止插件进程（命令式）或取消请求（常驻）。
- 僵尸回收：宿主必须回收子进程，避免僵尸进程堆积。

理由：v1 引入容器/沙箱会显著增加部署复杂度，且与「单二进制」定位冲突；进程隔离已能提供基本故障隔离与权限边界。

## 备选方案

| 方案 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. OS 进程隔离（推荐） | 独立进程 | 简单、跨平台、与单二进制一致 | 隔离强度有限（共用文件系统/网络） |
| B. 容器隔离 | 每插件一容器 | 强隔离、资源限制完善 | 需要容器运行时，违背部署简洁性 |
| C. 沙箱（seccomp/landlock 等） | 内核级限制 | 强度高 | 平台相关、实现复杂 |
| D. 进程内加载（Go plugin） | 无隔离 | 性能好 | 崩溃即宿主崩溃，排除 |

## 影响

**正面**：实现简单；跨平台可落地；插件崩溃不影响底座；与生命周期状态机自然衔接。

**负面 / 代价**：插件仍可访问其有权访问的文件与网络（受权限声明限制，但非内核级隔离）；资源限制能力依平台而异。

**迁移成本**：中等。若未来需要强隔离，可在「启动插件」抽象处替换为容器启动，但需要重新设计文件/网络权限模型。

## 约束

- 命令式插件调用超时后必须确保进程被终止（含其子进程组）。
- 常驻插件重启必须有限次；禁止无限快速重启（防雪崩）。
- 插件崩溃不得改变其安装/启用事实，只改变运行态。
- 资源限制参数若启用，必须有默认值与可配置项，禁止魔法数字散落代码。
- 健康检查不得有副作用（不得调用业务能力）。

## 验证方式

1. 杀死常驻插件进程 → 底座不退出，状态变为 unhealthy/重启，审计有记录。
2. 命令式插件死循环 → 超时后被杀，无残留进程。
3. 连续崩溃达到阈值 → 停止自动重启并明确告警。

## 待确认问题

- 是否确认仅 OS 进程隔离？
- 是否需要资源限制，若需要，采用何种机制？
- 重启退避参数与阈值上限？
- 连续失败是否自动禁用插件（建议不自动禁用，只标记 unhealthy）？
