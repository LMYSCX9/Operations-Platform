# ADR-0020 契约文件唯一来源、SDK 边界与代码生成工具链

- 状态：`accepted`
- 日期：2026-11-16
- 决策者：用户授权补全（gRPC/protobuf 依赖已在 ADR-0005 批准，本 ADR 定其工程落地方式）
- 关联：OQ-018、OQ-045、[ADR-0005](0005-daemon-rpc-transport.md)、[ADR-0012](0012-module-boundaries-and-sdk.md)、[DOC-03](../03-plugin-model.md) §5、[plugin-spec/03](../../plugin-spec/03-remote-protocol.md)

## 背景

ADR-0005 批准了 gRPC 与 protobuf 工具链，但没回答插件作者最常问的四个工程问题：

1. 生成代码要不要入库？我能不能直接拿到可用的包？
2. 我机器上没有 protoc 怎么办？protoc 与插件版本有什么要求？
3. `.proto` 到底以哪份为准——`docs/`、`plugin-spec/` 还是仓库里的代码？
4. SDK 里放什么、不放什么？

这四点不写死，每个插件都会各自选一种做法，最终出现多份互不一致的契约副本。

## 决策

### 1. 契约唯一来源：仓库 `sdk/`

| 项 | 结论 |
| --- | --- |
| 唯一事实来源 | `sdk/plugin/v1/plugin.proto`（服务定义、消息、字段编号、错误类别常量所在处） |
| 副本 | `plugin-spec/03-remote-protocol.md` 中的 proto 代码块是**副本**，必须与 `sdk/` 逐字一致（允许差异仅限于说明性注释） |
| 校验 | CI 执行「重新生成 + 与仓库对比」，任一处不一致即失败 |
| 修改权 | 只有底座仓库可以改 `.proto`；插件仓库只能引用，不得改动后再对外声明兼容 |

### 2. 生成物入库

`sdk/plugin/v1/` 下同时提交：

- `plugin.proto`
- `plugin.pb.go`
- `plugin_grpc.pb.go`

理由：

- **无 protoc 环境可用**：插件作者（尤其非 Go 语言、离线环境）可以直接使用仓库内已生成的代码，不必先搭工具链。
- **可审计**：契约变更在 diff 中可见，不依赖「谁在本地重新生成过」。
- **CI 可验证**：生成物与 `.proto` 是否同步可以用一条命令判定，不靠人工约定。

### 3. 工具链与版本要求

| 项 | 结论 |
| --- | --- |
| 生成入口 | 只允许 `scripts/gen-proto.ps1`（Windows）与 `scripts/gen-proto.sh`（Unix） |
| 版本锁定 | 工具版本**固定在脚本内**（`protoc`、`protoc-gen-go`、`protoc-gen-go-grpc`），具体版本号随落地锁定，登记 OQ-045 |
| 运行时依赖 | Go 侧 `google.golang.org/grpc`、`google.golang.org/protobuf`，由 `go.mod` 锁定；属 ADR-0005 已批准依赖 |
| 构建期工具 | `protoc` 与两个插件是**构建期工具**，不进入交付二进制，不是运行时依赖 |
| 版本匹配 | 生成的代码必须与 `go.mod` 中 `protobuf`/`grpc` 的主版本匹配；升级运行时库必须同批次重新生成 |
| proto 语法 | `proto3`；字段编号一经发布不得复用 |

### 4. 没有 protoc 时的替代路径

按优先级：

1. **Go 插件（推荐）**：直接 `import` 仓库内 `sdk/plugin/v1`，不需要 protoc。
2. **非 Go 插件**：使用目标语言的 protobuf 生成器，从 `sdk/plugin/v1/plugin.proto` 生成，并在插件仓库提交生成物或纳入构建流程。
3. **改用命令式形态**：若目标语言无法生成 gRPC 代码，应使用 `form: command`（stdio，无代码生成需求）。
4. **禁止**：手写与 `.proto` 等价的 RPC 桩 / 消息结构。手写桩无法被 CI 校验，是契约漂移的主要来源。

### 5. SDK 边界

`sdk/` 只允许包含：

- `.proto` 与生成代码；
- 契约常量（错误类别、退出码、契约版本）；
- 与契约直接相关的纯类型/辅助函数（如版本区间解析的口径说明）。

`sdk/` **不得**包含：

- 宿主实现、`internal/` 任何包、数据库、配置加载、日志实现；
- 业务逻辑或「方便插件开发」的框架;
- 对底座运行时的隐式依赖（插件可以只用 SDK 类型而不链接底座代码）。

SDK 的**发布形态**（独立 Go module / 仓库内包路径）仍待 OQ-018；但无论形态如何，上述文件位置、内容与生成规则不变。

## 被否方案与原因

| 方案 | 说明 | 否决原因 |
| --- | --- | --- |
| 生成物不入库，构建期生成 | 仓库干净 | 每个插件环境都必须装 protoc 与插件，离线/受限环境不可行；CI 无法判断是否漂移 |
| 只发 `.proto`，不提供生成代码 | 语言中立 | 与上一条同因；且会诱导手写桩 |
| 运行期动态解析 proto（反射） | 无需生成 | 引入运行时依赖与性能开销，错误在运行期才暴露 |
| 允许插件各自维护 proto 副本 | 灵活 | 多份契约必然漂移，兼容性判定失去依据 |
| 手写等价 RPC 桩 | 不依赖工具链 | 字段编号/默认值/可选性极易写错，且不可校验 |
| protoc 作为运行时依赖 | 统一版本 | 交付二进制不应依赖外部工具；ADR-0001 单二进制约束 |
| SDK 直接复用 `internal/` 包 | 省事 | 会把宿主实现暴露给插件，破坏模块边界（ADR-0012） |

## 影响与约束

**正面**：插件开箱可用；契约只有一份；生成物可审计；CI 能机械校验一致性。

**负面 / 代价**：仓库体积增加；每次契约变更都要重新生成并提交；`protoc` 版本升级需要同步脚本与生成物；
非 Go 语言插件仍需自备生成器（但可用命令式形态规避）。

**实现约束**：

- 底座构建不依赖 `protoc`（生成物已入库），只有改契约时才需要工具链。
- 生成脚本必须可在干净环境重复执行；脚本失败即视为契约变更未完成。
- `plugin-spec/03` 的 proto 副本必须标注「以 `sdk/` 为准」。

## 验证方式

1. 干净克隆后 `go build ./...` 成功，不要求本机安装 protoc。
2. 修改 `.proto` 字段编号但未重新生成 → CI 失败并指出生成物过期。
3. 手工修改 `plugin.pb.go` → CI 失败（重新生成后 diff 非空）。
4. `plugin-spec/03` 的 proto 与 `sdk/` 不一致 → 文档校验失败。
5. 非 Go 插件按 `.proto` 生成的客户端能完成 `Invoke`（用样例插件冒烟）。

## 遗留待定

- SDK 发布形态（独立 module 名称与版本策略）：OQ-018。
