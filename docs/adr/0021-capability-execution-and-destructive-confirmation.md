# ADR-0021 能力执行模型与高危操作确认语义

- 状态：`accepted`
- 日期：2026-11-16
- 决策者：用户授权补全（能力一律串行、移除交互式 setup、version 不占能力、高危操作确认写成通用契约）
- 关联：OQ-006（decided）、[ADR-0003](0003-plugin-discovery-registration.md)、[ADR-0005](0005-daemon-rpc-transport.md)、[DOC-03](../03-plugin-model.md) §4、[plugin-spec/01](../../plugin-spec/01-manifest.md) §3、[plugin-spec/04](../../plugin-spec/04-io-conventions.md)

## 背景

插件能力清单此前只有「一个能力一个明确动作」的定性要求，缺少三条可执行规则，导致每个插件都要单独约定：

1. 同一插件的多个能力能否并发执行——尤其 delete / restore / gc 这类会改变目标状态的写操作。
2. 是否允许用 `setup` 能力做初始化——这类能力往往隐含「等用户输入」，与「禁止 TTY」冲突。
3. 是否允许用 `version` 能力报告版本——与 `GetVersion`、清单 `version.plugin` 重复。
4. 「高危操作需要确认」到底是口头约定还是契约；确认字段叫什么、谁校验。

这些都属于「不写死就必须每次来问」的问题，因此一次性纳入通用契约。

## 决策

### 1. 调度：所有能力一律串行

| 项 | 结论 |
| --- | --- |
| 调度模型 | 底座为**每个插件**维护单一执行队列，同一插件的任意两个调用不并发（跨能力亦串行） |
| `concurrency` 字段语义 | 保留，含义改为「插件自身是否线程安全」的**承受能力声明**；**不**改变底座调度 |
| `parallel` | 底座仍串行调用；插件不得据此假设会收到并发调用 |
| `serial` | 与全局串行一致 |
| 跨插件 | 不同插件之间可并发，受底座全局并发上限约束（OQ-017/OQ-039） |

理由：高危操作的可审计性与可回滚性依赖确定的执行顺序；串行让「同时两个 delete」「restore 与 gc 交错」这类不可解释状态不可能出现；
v1 的调用量也不需要在单插件内并行。将来若放开，必须证明对 `destructive` 能力的隔离方案，属 MAJOR 契约讨论。

### 2. 移除交互式 setup

- **禁止**依赖 TTY、禁止从 stdin 读取额外输入（两种形态都适用；命令式插件 stdin 只承载一行请求）。
- 初始化必须**幂等**、可在无交互环境下重复执行；所需参数一律通过能力输入或 `--ops-config` 提供。
- 不允许声明「等待用户确认/输入」的能力；底座不会提供任何交互通道。
- 若插件确需初始化步骤，应实现为普通能力，并满足：幂等、无交互、失败可诊断；是否幂等必须在清单 `idempotent` 中如实声明。

### 3. `version` 不单独占能力

| 形态 | 版本来源 |
| --- | --- |
| 命令式 | 清单 `version.plugin`（响应中的 `plugin_version` 可选，且必须与清单一致） |
| 常驻 | `GetVersion` RPC（返回 `plugin_version` 与 `contract_version`）+ 清单 |

因此禁止声明能力名末段为 `version` 的能力（如 `demo-agent.version`）；底座在语义校验阶段拒绝。

### 4. 高危操作确认：契约强制

新增清单字段 `capabilities[].risk_level`：

| 取值 | 含义 |
| --- | --- |
| `normal` | 默认值，普通读写 |
| `destructive` | 不可逆或大范围影响（删除、覆盖恢复、回收） |

规则（均为**契约强制**，不是建议）：

1. 能力名末段为 `delete` / `restore` / `gc` 时，`risk_level` 必须为 `destructive`；缺失或声明 `normal` → 安装校验失败。
2. `destructive` 能力的输入 schema 必须把确认字段列为 `required`：
   - `delete`：`confirm_partition`；
   - `restore` / `gc`：`confirm`，以及目标字段（`target` 或 `partition`，以能力 schema 为准）。
3. 确认值的校验在**插件侧执行，且必须先于任何副作用**：
   - `delete`：`confirm_partition` 必须**严格等于**同请求中的目标分区标识（区分大小写、不做模糊匹配）；不相等 → `validation_failed`。
   - `restore` / `gc`：`confirm` 必须为 `true`；缺失或为 `false` → `precondition_failed`（未获确认，拒绝执行）。
   - 目标字段缺失 → `input_invalid`。
4. 底座侧校验（静态 + 调用前）：
   - 静态：能力名与 `risk_level` 一致性、schema `required` 是否包含约定字段；
   - 调用前：对 `destructive` 能力写审计（记录 `confirm` 字段是否出现，**不记录其后的业务数据**），并在 UI 侧要求二次确认；
   - 底座**不**校验确认值与目标是否一致——底座不理解目标语义，越权校验会制造假安全。
5. 直接调用 API 的调用方必须自行携带确认字段；缺失时由插件拒绝，底座不做兜底填充。

## 被否方案与原因

| 方案 | 说明 | 否决原因 |
| --- | --- | --- |
| 允许同一插件内并行 | 吞吐更高 | `destructive` 能力交错后无法解释执行顺序，审计与回滚失去意义 |
| 用 `setup` 能力做初始化 | 直观 | 往往隐含交互输入，与「禁止 TTY」冲突；初始化应幂等且无交互 |
| 用 `version` 能力报版本 | 插件自治 | 与 `GetVersion`/清单重复，出现两个事实来源 |
| 高危确认只写进文档、不做校验 | 灵活 | 每个插件各写一套字段名，调用方无法通用；等于没有契约 |
| 底座统一校验确认值 | 集中安全 | 底座不知道目标语义，无法判断「严格相等」；只能做存在性与类型校验 |
| 用布尔 `dangerous: true` 代替 `risk_level` | 少一个枚举 | 与既有 `sensitive`（数据敏感性）语义混淆；`risk_level` 表达操作后果，两者正交 |
| 由 UI 二次确认即可，不要求字段 | 体验好 | API 直调与定时任务可绕过 UI，确认必须落在契约层 |

## 影响与约束

**正面**：高危操作有统一字段与校验点；调用方可以用同一套规则保护自己；并发不可解释状态被从根上消除。

**负面 / 代价**：单插件吞吐受限（v1 可接受）；清单多一个字段；命令式插件也要承担确认校验；
`parallel` 声明不再带来性能收益，插件作者可能误以为声明无效（需在 FAQ 中说明）。

**实现约束**：

- 底座调度器必须按插件维度串行，不得因 `parallel` 声明绕过。
- 语义校验必须拒绝 `version`/`setup` 能力名与 `destructive` 标记不一致的清单，错误定位到能力路径。
- 定时任务与 UI 调用走同一校验路径，不得在任一入口豁免确认字段。

## 验证方式

1. 同一插件两个能力被并发调用 → 实际串行，执行记录顺序可解释。
2. 清单声明 `demo-agent.version` → 校验失败并指出能力路径。
3. `delete` 能力 `risk_level: normal` → 校验失败。
4. `delete` 输入 `confirm_partition` 与目标分区不一致 → 返回 `validation_failed`，无副作用。
5. `restore` 输入缺少 `confirm` 或为 `false` → 返回 `precondition_failed`，无副作用。
6. 定时任务调用 `destructive` 能力且未带确认字段 → 与 API 调用同样被拒绝。
7. `destructive` 能力被调用 → 审计包含确认字段存在性与调用主体，不含业务数据。

## 遗留待定

- `destructive` 能力的二次确认交互形态（UI 交互细节）：随前端规格（OQ-013）。
- 高危操作审计字段集：OQ-016。
- 是否允许 `restore` / `gc` 批量目标：随能力 schema 定义，不改变本 ADR 规则。
