# ADR-0012 模块边界、契约版本与插件 SDK 形态

- 状态：`proposed`（版本规则与契约文件边界已于 2026-11-16 定稿；SDK 发布形态仍待 OQ-018）
- 日期：2026-11-16（版本规则定稿）
- 决策者：用户（P0 六项批准；SDK 形态未定）
- 关联：OQ-006（decided）、OQ-018（open）、[DOC-05](../05-extension-points-and-compatibility.md)、[ADR-0003](0003-plugin-discovery-registration.md)、[ADR-0004](0004-stdio-wire-protocol.md)、[ADR-0005](0005-daemon-rpc-transport.md)

## 背景

插件必须能「脱离底座源码」开发（G-5）。这要求契约（类型、协议、校验规则）以可复用形式对外发布。
同时底座内部代码需要清晰边界，避免插件开发反向依赖底座内部实现。

## 一、已定稿部分（本次同步定稿）

### 1. 契约版本规则（OQ-006 结论）

| 项 | 结论 |
| --- | --- |
| 版本形式 | `MAJOR.MINOR`（不使用 PATCH 表达契约变化） |
| MAJOR | 破坏性变更：删除能力/字段、改变字段语义或必填性、改变通信语义、改变错误码含义 |
| MINOR | 向后兼容增量：新增可选字段、新增能力、新增扩展点 |
| 编辑器性修正 | 不改版本 |
| 插件声明 | 插件必须声明其**支持的契约版本范围**（而非单一版本） |
| 底座支持 | 底座**同时支持同一 MAJOR 下的多个 MINOR**，并对外公布支持的 MAJOR 集合 |
| 判定时机 | 安装/启用时完成兼容判定并记录结果，不等到首次调用 |

插件侧声明写法（已定）：

```yaml
version:
  contract: ">=1.0 <2.0"   # 空格分隔的约束集合，操作符支持 >=、<、=
```

- 约束集合必须与底座支持的 MAJOR 集合有交集，否则拒绝安装。
- 禁止声明「任意版本兼容」。

### 2. 契约唯一来源与模块边界

| 边界 | 结论 |
| --- | --- |
| 契约文件位置 | 全部契约（proto 定义、清单 JSON Schema、错误模型、错误码/退出码常量、契约版本常量）**只**存在于 `sdk/` |
| 底座内部 | `internal/` 下实现只允许从 `sdk/` 引用契约，禁止在 `internal/` 内另定义一份契约副本 |
| 插件仓库 | 只依赖 `sdk/` 与公开契约即可编译，不得 import 底座 `internal/` 包 |
| 版本常量 | `sdk/` 必须提供「底座支持的契约版本范围」与「当前契约版本」常量，供插件自检（CAP-11） |

建议目录（结构约定，落地时以实际仓库为准）：

```text
Operations-Platform/
├── cmd/                 # 入口（单二进制）
├── internal/            # 底座内部实现，外部不可 import
│   ├── plugin/          # 发现、注册、生命周期、执行器
│   ├── gateway/         # 调用网关
│   ├── authz/           # 身份与授权
│   ├── store/           # 持久化
│   ├── config/          # 配置加载与校验
│   ├── api/             # 对外接口层
│   └── observability/   # 日志与指标
├── web/                 # 前端源码与构建产物（构建期）
└── sdk/                 # 插件 SDK 与契约（对外唯一来源）
```

### 3. 已批准的依赖

- gRPC 与 protobuf 工具链（运行时 + 代码生成）随 [ADR-0005](0005-daemon-rpc-transport.md) 一并批准引入。
- 契约校验所需的 JSON Schema 校验器属于清单校验的实现依赖，其具体库在落地时随 `go.mod` 锁定；
  规格不预设库名与版本。
- 除上述，本 ADR 不批准其他新依赖。

## 二、仍待定部分

### 4. SDK 发布形态（OQ-018）

- 推荐：`sdk/` 自带 `go.mod`，作为**同仓库独立 module** 发布；插件仓库通过 module 依赖 + 版本号引用（本地开发用 `replace`）。
- 备选：独立仓库发布、仓库内普通包、仅协议文档。
- 状态：**未定**，本 ADR 保持 `proposed` 直至 OQ-018 关闭。

## 被否方案与原因（针对已定稿部分）

| 方案 | 说明 | 否决原因 |
| --- | --- | --- |
| 契约版本用完整 SemVer | `MAJOR.MINOR.PATCH` | 契约无「补丁级」语义，PATCH 会诱导把破坏性变更当补丁发；两者混用导致兼容判定含糊 |
| 底座只支持单一契约版本 | 一次只支持一个 MINOR | 底座升级必然逼所有插件同时升级，运维不可行 |
| 插件声明单一精确版本 | `contract: 1.0` | 底座升 MINOR 即误判不兼容，产生大量假拒绝 |
| 契约副本分别放在 `internal/` 与 `sdk/` | 各自维护 | 必然漂移，是「实现与契约不一致」的根源 |
| 插件直接 import 底座内部包 | 省事 | 破坏封装边界，插件与底座实现强耦合，升级即破坏 |

## 影响与约束

**正面**：契约单点维护；插件独立演进；`internal/` 保证封装边界；兼容判定有确定规则。

**负面 / 代价**：多模块构建与发布流程稍复杂；`sdk/` 的 tag 与底座版本需要人工/脚本对齐。

**实现约束**：

- 契约变更必须能追溯到 ADR；`MAJOR` 变更需新增 ADR。
- 禁止在 `sdk/` 中出现底座内部实现依赖。
- 契约文件变更必须同步更新 `plugin-spec/` 中对应的字段说明与示例（文档即代码）。

## 验证方式

1. 插件声明 `">=1.0 <2.0"`，底座支持 1.0/1.1/1.2 → 安装通过，且记录命中的 MINOR。
2. 插件声明 `">=2.0 <3.0"`，底座仅支持 1.x → 拒绝安装，错误指出无交集。
3. 修改 proto 字段名但不升 MAJOR → 兼容性校验/评审环节应拦截（作为流程缺陷记录）。
4. 新建插件仓库只依赖 `sdk/` 即可编译（无 `replace` 指向内部包）。
5. `internal/` 下的包无法被外部 module import（编译期验证）。
