# ADR-0001 单二进制交付与前端资源内嵌方式

- 状态：`proposed`
- 日期：2026-11-16
- 决策者：待定（用户）
- 关联：OQ-014、[DOC-06](../06-non-functional-requirements.md) §1

## 背景

前端与后端必须打包为一个二进制文件。需要决定前端构建产物如何进入 Go 二进制，以及构建流水线的形态。

## 决策（待确认）

采用哪种内嵌机制，以及构建顺序、开发期是否允许分离运行。

## 推荐方案与理由

**Go 标准库 `embed` + 构建脚本（推荐）**

1. 先构建前端，产物输出到 `web/dist`（路径待定）。
2. Go 代码通过 `embed.FS` 将 `web/dist` 编入二进制。
3. UI 由 Go HTTP 服务直接提供静态文件，无需额外运行时。

理由：零第三方依赖、官方支持、产物可预期、与「单二进制、无外部运行时」的目标一致。

## 备选方案

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| B. 代码生成式内嵌（go-bindata 类工具） | 生成含字节数组的 Go 文件 | 可完成目标，但引入工具链与巨大源文件，构建变慢 |
| C. 第三方打包器 | 使用社区打包工具 | 增加依赖与升级风险，收益不明确 |
| D. 运行时读取外部目录 | 不内嵌 | 直接违背项目目标，排除 |
| E. 反向代理外部静态服务 | 分离部署 | 违背单二进制目标，排除 |

## 影响

**正面**：交付简单；部署只需一个文件；版本一致性强（前后端不会错配）。

**负面 / 代价**：每次前端改动都要重新编译二进制；开发期需要前后端分离运行（dev 模式）；二进制体积随前端资源增长。

**迁移成本**：低。内嵌方式对业务代码影响小，主要影响构建脚本与本地开发流程。

## 构建约束（待细化）

- 前端产物必须先于 Go 构建生成；缺少产物时构建应**失败**而不是产出空 UI。
- 是否需要构建时校验产物完整性（例如入口文件存在）：建议需要。
- 是否提供 `-tags` 跳过内嵌的 dev 模式：建议提供。
- 目标平台与架构清单：待定（OQ-014）。
- 是否要求可复现构建（固定构建时间戳、路径）：待定（OQ-014）。

## 验证方式

1. 删除前端源码目录后，仅用二进制启动，UI 可正常访问。
2. 在无 Node/Python/JVM 的干净环境中启动成功。
3. 二进制自检接口能报告前端资源版本/摘要（如采用）。

## 待确认问题

- 内嵌方案是否确认为 `embed`？
- 是否需要 dev 模式跳过内嵌？
- 目标平台清单与可复现构建是否纳入 v1 验收？
